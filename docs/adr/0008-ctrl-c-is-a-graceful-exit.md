# ADR-0008：Ctrl+C 是正常退出，不是硬杀

- 状态：采纳（2026-09）
- 背景：用户报告「Ctrl+C 把终端关掉了」。现象指向硬杀：**被 SIGINT 当场杀掉的进程不会还原终端**——它留在 alt 屏、光标仍然隐藏，看起来就像终端被关掉或卡死了，而且汇总报告一个字都不会打出来。
- 事实：`Ctrl+C` 有两条路径到应用。
  1. **raw 模式下**（正常运行时）它是 `\x03` 这个字节，由 `app.ts` 的全局输入监听接管，走 `shutdown()`：中止当前场景 → 取消全部待办 → 还原终端 → 打印汇总报告 → 退出。
  2. **raw 模式没生效的时刻**——启动早期、以及收尾里 `tui.stop()` 还原终端之后——终端把它变成 **SIGINT 信号**。而 `src/index.ts` 只挂了 `uncaughtException` / `unhandledRejection`，**没有任何 SIGINT 处理**，于是默认行为生效：当场杀掉进程。第 2 条路正是「终端被关掉」的来源，尤其在收尾阶段（用户嫌慢又按了一下 Ctrl+C）最容易踩到。

## 决策一：SIGINT 接到同一条收工路径

不新增第二套退出逻辑：信号处理器只做一件事——调 `requestShutdown()`，和按 `Ctrl+C` 完全同义。这样「字节」与「信号」两条来源收敛到同一个收尾流程，行为不可能漂移。

## 决策二：第二次收工请求 = 不再等队列，但仍然走完收尾

`shutdown()` 会等队列真正停下（最长 30s，防止日志写进已销毁的视口）。收尾期间再收到一次收工请求（按键、信号、`/exit` 三者同义）时，**跳过等待**立刻收尾，但**不跳过**还原终端与打印报告。

理由：用户按第二次表达的是「我不想再等了」，而不是「把报告和终端还原也掐掉」——把收尾掐掉正是这次要修的硬杀体验。取消「等队列」与取消「收尾」是两件事，这里只取消前者。

## 决策三：`process.on("exit")` 兜底还原终端

异常把进程带走时（`uncaughtException` → `process.exit(1)`）也保证终端不会留在 alt 屏。`TuiBase.stop()` 是**同步且幂等**的（`beforeTerminalStop`/`afterTerminalStop` 在 `altScreenActive` 为假时直接返回，已用无头探针核对：连调两次只会退出一次 alt 屏、光标只显示一次），因此放在 `exit` 钩子里是安全的。

## 决策四：不做「收尾期间忽略 SIGINT」

忽略会让用户「按了没反应」，而且在真的卡住时把最后一条出路也堵死。正确的做法是给一条**真的能走通**的路：第二次请求 = 立刻收尾。

## 未采纳的方案

- **SIGINT 直接 `process.exit(130)`**：等于把硬杀换个写法，终端照样留在半途。
- **启动早期也接管 SIGINT**：那时还没进 alt 屏，硬杀不会破坏终端；而接管会让「一个场景都没开始」的空会话走到「打印空报告」那一步，反而制造出更糟的观感。
- **收尾时阻塞等队列 + 提示用户等待**：`Ctrl+C` 的语义是「我不想再等了」（ADR-0002 决策五），阻塞与提示都是对它的否定。

## 影响

- `src/tui/app.ts`：新增 `requestShutdown()`（第二次请求置 `finishNow`）、`finishNow` 状态、SIGINT 处理器、`process.on("exit")` 兜底；`Ctrl+C` 按键与 `/exit` 都改走 `requestShutdown()`。
- `src/i18n.ts`：`tui.shutdownNow`（第二次请求的说明）与 `tui.signalReason`（信号来源的标注，便于从日志判断「字节没到、走了信号」）。
- README 两个语种：键位表与说明。
