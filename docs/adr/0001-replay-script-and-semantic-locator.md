# 回放脚本用语义定位符，且回放默认不调用任何模型

状态：accepted

页面用例每次都由 LLM 解析，慢、贵，且同一条用例两次跑法可能不同。但一条用例被跑通一次后，它的操作序列（点哪个元素、填什么值、断言什么）就是确定的。因此 pageqa 在带模型的运行中录制**成功执行过**的动作与断言，固化为回放脚本（`*.replay.json`），由 `pageqa --replay` 零模型重跑。

## 决策一：元素定位存语义定位符，不存 `@eN`，也不存 CSS 路径

定位符 = 角色 + 可访问名 + 同名序号（如 `link "Learn more"` 的第 1 个），录制时同时保留模型当时给的 target 作为兜底。

理由：bsk 的 `@eN` 只在产生它的那次快照内有效，回放时编号必然重排，直接存等于不能回放；CSS 路径对现代前端（`v-if`、组件库生成的动态 class）很快烂掉；而角色 + 可访问名是 bsk 快照本来就给出的稳定语义信息，页面小幅改文案、换节点后仍能重新命中。同名多元素（列表中每行都有「操作」按钮）靠「同名序号」区分，避免点错行。

兜底顺序：语义重定位 → 录制时的 target（是 CSS 就还能用）→ 明确报错。**不做「猜一个最像的元素」**：点错元素制造的是假通过，比失败更危险。

定位符还记录**祖先路径**（如 `menu "Dropdown List"`、`tabpanel "结构"`）。起因是实测踩坑：PLM 详情页同时存在页面级的「操作」下拉与区域级的「操作」下拉，名字完全相同；只按「同名第几个」（`nth`）在页面元素数量变化后会指错，回放点开了错误菜单（菜单项是「待办事项／产品管理」，而脚本要的是「上传文档」），后续 7 步连锁失败。快照的缩进本身就是层级，因此把「这个元素在哪个区域之下」记下来，回放时按最深层的连续匹配度消歧，比序号抗漂移。路径条目做了截断（60 字符）与层数限制（最深 3 层）：`main` 这类节点的可访问名可能是整页文本，存进去既撑大脚本又永远匹配不上。

定位失败时不再只报「未找到」，而是区分三种线索写进报告：名字相近的元素存在（改名了）／该角色元素存在但名字都不同（多半点错了另一个同名菜单）／该角色元素一个都没有（菜单、弹窗并未打开）。这条改进直接把上面那次连锁失败从「不知道哪错了」变成「菜单开着，但是另一个操作下拉」。

## 决策二：回放默认零模型（字符串断言），`--semantic` 才用 Jev

回放的价值是确定性、快、免费，默认不能碰任何远端服务。代价是：若录制时启用了 Jev，模型可能给出「标题包含 Example」这类语义化断言，字符串包含匹配会误报失败。因此脚本会把在 Jev 下录制的断言标记为语义断言，回放失败时提示「可加 `--semantic` 重试」，而不是让人盯着一个没有解释的「不成立」。

## 决策三：脚本里的运行时取值以占位符形式保存

用例里的 `${timestamp}` 在运行时被展开成具体值，模型看到并操作的是展开后的值（`自动化测试产品202609211103`）。如果把这串具体值原样写进脚本，脚本就只能跑一次——第二次不是撞名就是断言失败。

因此录制时用同一时刻的取值反查，把具体值还原成 `${timestamp}`（保留 `recordedValue` 作为「这次真正填了什么」的证据），回放时重新展开、同一次回放共用一个时刻。还原范围必须覆盖**定位符里的可访问名**：列表里点的是「刚创建的那条」，名字里也带时间戳，漏掉它回放必然定位失败——这是实测踩到过的坑。

同理，脚本自带 `recorded*` 字段这一事实使旧脚本可以**在加载时自愈**：据此反推出写死的取值并还原，无需为了一个字段重跑十几分钟的 LLM 用例。

## 决策四：元素未找到按「跳过」处理，其余失败记录后继续（推翻最初的「失败即停」）

最初的设计是「每步失败重试一次，仍失败即停止该场景」。第一次真实长流程回放就打脸了：65 步的 PLM 用例在第 12 步停住，原因只是**录制期模型补点了一下「取 消」**——提交后弹窗没关，模型顺手点取消关掉它；回放时页面更顺利、弹窗早已关闭，那个按钮根本不存在。一条长流程因为一个非关键动作整条报废，后面 53 步什么信息都拿不到，为了让回放可用，只能手工反复删步骤重跑。

改为：

- **元素未找到** → 记为「跳过」并继续，**不算失败**。元素不存在表达的是「当前页面状态下这一步不需要」，而不是页面退化的证据；真正的退化会由后续步骤或断言暴露出来（例如提交按钮被改名，后续「断言列表出现新记录」就会失败）。代价是：若某元素被删掉而用例对它没有任何断言，这一步的消失不会被察觉——可接受，因为这种步骤本就不影响用例结论。
- **其它失败（含断言不成立）** → 记为失败并**跑完剩余步骤**，一次给出整条用例的健康报告。失败照样进报告、照样让退出码非零，所以不牺牲诚实性。
- **navigate 失败** → 中止，后续步骤已无意义。
- `--fail-fast` 保留「任一失败即停」的旧行为，供快速排障。

另外钉死一条教训：结论判定必须**同时**看「步骤失败」与「断言不成立」。中途重构时曾只统计抛出的步骤失败，于是带 FAIL 断言的用例报了 PASS 与退出码 0——假通过比报错危险得多，因此判定逻辑抽成纯函数 `replayScenarioStatus` 并由单测覆盖。

## 考虑过的其他方案

- **直接存 `@eN`**：改动最小，但只在同一次快照内有效，等于不能回放。
- **存 CSS 路径（用 `bsk get-html --ref` 反推）**：对静态页面够用，但要对每次交互多付一次 bsk 往返，且对组件库生成的动态 class 不稳定。
- **回放沿用录制时的 Jev 配置**：断言更宽容，但把外部服务的波动引入了本该确定性的回放。
- **生成能脱离 pageqa 运行的 shell/bsk 脚本**：看着直观，却丢掉断言、报告、退出码与 session 生命周期，无法充当 CI 门禁。
- **回放时自动重录（失败就退回 LLM）**：会让「不调用大模型」这一承诺失效，也让回放结果不可预测；改为在报告里点明失败步骤与对应用例原文，由人决定是否重新生成脚本。
