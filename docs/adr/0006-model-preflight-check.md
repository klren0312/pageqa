# ADR-0006：跑用例前先探活模型，不通就不执行

- 状态：采纳（2026-09）
- 背景：模型端点不通时（本地反代没起、`baseUrl`/`apiKey` 写错、模型名已下线），pageqa 仍会把整队场景逐条跑下去：每条都先开一个浏览器窗口、再等一次 LLM 请求失败，报告里堆出一片「用例失败」。一次配置错误被摊成 N 个假失败，真正的原因（连不上）沉在最上面一行日志里，几分钟就烧掉了。诉求很直接：**跑用例前先判断模型能不能联通，不通就别执行。**

## 决策一：探活走与真实运行同一条路

`probeModel()`（`models.ts`）用同一个 provider 的 `streamSimple` 发一次极小请求（`max_tokens=16`），而不是自己发一个 HTTP 探测（`HEAD /v1/models` 之类）。理由：探活走另一条路时，「探活通过、真跑不通」的裂缝正是最坑人的那种——鉴权、端点拼接、兼容参数、模型 id 的差异全在那条缝里。代价是每次探活都是一次真实请求（几个 token），显式接受。

## 决策二：每个场景开跑前都探，而不是只在启动时探一次

模型可能是**上个场景跑到一半**才断的：「启动那次通过了」不代表第 8 个场景时还通。只在启动时探一次，等于把这个问题原样留给长流程——而长流程正是 pageqa 的主场景（一次十几分钟）。成本是每个场景多一次 `max_tokens=16` 的请求，与十几分钟的运行相比可忽略。

## 决策三：探活发生在建 session 之前

检查位置在 `initializeAgent()` 里 `ensureBskReady()` / `ensureSession()` **之前**。理由：模型连不上却先把浏览器窗口开起来，既白等十几秒，也留下一个「看起来已经跑起来了」的现场——而那正是用户抱怨的那种观感。

## 决策四：失败用类型化错误，两种模式各自给出正确处置

探活失败抛 `ModelUnreachableError`（带 provider / model / 原因），而不是返回一份「失败报告」：

- **批处理**：stderr 打印可读原因 + 出路（`/model`、`/login`、检查 `config.json`），退出码 `1`，**stdout 不打印报告**——一条用例都没执行，就不该出现一份看起来像结果的报告。
- **交互模式**：该场景如实记为 **FAIL**，并把**剩余待办全部取消**。不记为「已取消」是因为那个类别「不计入退出码」（ADR-0002 决策五），把「模型连不上」混进去会让 CI 把它当成通过；不保留待办继续排队是因为队列没有暂停语义，且「停在那里什么都不做、退出码 0」同样会被当成通过。取消是队列已有的、会被如实上报的停法（`cancelAllWaiting` + `/status` 与汇总报告都会写明）。

## 决策五：必须显式检查 `stopReason === "error"`

pi-ai 的请求失败**不抛异常**：它 resolve 一条 `stopReason: "error"` 的消息（见其 `api/lazy.ts` 的 `createSetupErrorMessage`）。只看「有没有 throw」会把「连不上」判成「通了」，探活就成了摆设。这是本 ADR 里最容易写错的一行，已在 `tests/model-catalog.test.mjs` 里钉死。

## 决策六：用户按 Esc 造成的中止不算「不可达」

Esc 表达的是「我不想再等这个了」，不是「模型不通」。因此探活期间被中止（或开跑前就已被 `/cancel`）一律交给既有的取消路径：记为「已取消」，不进退出码、不写入回放脚本。

## 未采纳的方案

- **自己发 HTTP 探测**：更快更省，但探的是另一条路，见决策一。
- **只在进程启动时探一次**：抓不到「跑到一半断线」，见决策二。
- **探活失败时重试几次**：连接被拒/鉴权错误不会因为重试而变好，只会把「立刻告诉你」变成「等三倍时间」。
- **不通时给每个场景各记一条失败（现状）**：正是本次要修的痛点。
- **不通时保留待办排队、等下一条指令再试**：退出码会是 `0`，CI 于是把「模型连不上」当成通过；且队列停在「什么都不做」的状态会被误读成「正在等」。
- **新增 `--no-probe` 开关**：探活是「不跑假失败」的保障，不是可选优化；真跑得通时它只花几个 token。真需要绕过时，`--replay` 本身就是零模型的路径。

## 影响

- `models.ts`：新增 `probeModel()`（含 20s 超时与「端点没给原因」的兜底文案）。
- `agent.ts`：新增 `ModelUnreachableError` 与 `ensureModelReachable()`；`initializeAgent()` 在 bsk 就绪检查之前探活，探活通过后才打印「LLM 已就绪」。
- `index.ts`：批处理 catch 分支识别 `ModelUnreachableError`，给干净报错与出路（不打印栈）。
- `tui/app.ts`：场景执行器识别 `ModelUnreachableError`，记为 FAIL（断言写成「模型可连通」）并停掉整条队列。
- 测试：`tests/model-catalog.test.mjs` 覆盖探活（成功 / `stopReason=error` / 超时说人话 / Esc 不算不可达 / 错误类型可区分）；`tests/tui.test.mjs` 覆盖「执行器里停掉整条队列」。
