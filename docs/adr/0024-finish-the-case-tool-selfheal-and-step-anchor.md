# ADR-0024：用例要能跑完——工具层自愈 + 每轮进度锚

- 状态：已采纳 · 日期：2026-11-18
- 相关：ADR-0014（上下文预算与压缩）、ADR-0022（缺陷与失败分离）

## 背景

一条 22 步的用例跑了 **159 轮**、355.9s、判 FAIL，而其中 3 条断言**全部成立**——页面上的事基本都做对了，流程却没走完。日志（`pageqa-2026-11-18.log` 第二次运行）把失败分成了三类，彼此不相干，但叠加起来足够把一条用例拖死：

| 现象 | 次数 | 真实性质 |
| --- | --- | --- |
| 点击失败 `target_covered` | ~9 | 命中测试在**派发前**失败，点击没有发生（`effect_state: none`） |
| 操作被拒 `reference context expired` | ~10 | 权限闸门在**落到 CDP 之前**返回，动作没有派发 |
| 熔断拒执行 | 8 | 拦在了执行前，但模型照样被调用一轮 |
| 前期空转 | 21 轮 | `navigate` 同一 URL 成功 5 次、`wait_for` 6 次、`snapshot` 4 次，**全部成功** |

四件事被这份数据钉死：

1. **可恢复的失败被当成不可恢复的**。`observation_required` 会 sync + 重发，而由 `render_error.rs` **同一个权限分支**渲染出来的 `reference context expired` / `control_context_invalid` 却落进了「只 sync、把失败交回模型」的分支。这两族失败都发生在动作派发之前，重发一次不会变成「点了两次」——却每次都要模型自己「失败 → snapshot → 再点」，白付两轮往返（≈3s）。
2. **`target_covered` 完全没有恢复路径**。bsk 的 hint 明写 `synchronize before clicking`，pageqa 只是把原文透传给模型。日志里紧接着的那一次同样的 click 往往就成功——遮挡是抽屉/浮层收尾时的瞬时状态。
3. **熔断只统计失败**。前 21 轮 15 次调用**全部成功**，失败熔断一次都没触发。同一动作重复成功没有任何辩解空间：页面并没有因此往前走，第 4 次不会带来新信息。
4. **模型拿不到机械进度**。「必须按编号顺序执行」只在系统提示里说过一次，一轮工具结果之后就退到几千 token 之外。模型手上没有「我在第几步、下一步那句话是什么」的读数，于是用「再 navigate 一次确认页面」代替推进——22 步跑出 159 轮，主体成本在这里，不在失败本身。

另有一条**判反了**的用例：页面 22 步全跑完、4 条断言全过、建单成功，却因 `select_option` 失败被记为「未恢复的工具失败」而判 FAIL。模型其实换了路径（`click` 展开 → `snapshot` → `click` 选项）把事情做成了，旧口径只认**同名工具**恢复。

## 决策

### 一、动作派发之前失败的，自动重发一次

1. **权限闸门拒绝统一识别**（`isStrictObservationRefusal`）：`observation_required`、`reference context expired`、`requires a valid control context from cooperate sync` 三种都走「`cooperate sync` → 重发一次」。判定依据是它们**都发生在落到 CDP 之前**，不是按文案逐条打补丁。人接管、换标签页、沙箱归属那一族仍然只 sync 不重放——它们可能已经生效，或需要人来处理。
2. **`target_covered` 自愈**（`isCoveredTargetError`）：`cooperate sync` → `scroll-to` → 重试一次。IPC 路径看结构化 `reason`，CLI 路径看渲染文案，两条路都要认得出。
3. **每种恢复在同一次动作里最多做一遍**（`once(kind)`）。重试再失败就把失败往上报，不靠重试自旋——原来 `element_not_visible` 分支重试再失败会无限递归，一并收进这条约束。
4. **`select_option` 不再整条判死**：展开点击重试后仍失败，改走「`click` 展开 → 读快照 → 按文本点选」这条已在探针不可用时验证过的通道。

### 二、重复成功要和重复失败一样被拦

5. **同一动作连续成功 3 次后拒绝第 4 次**（`REPEAT_SUCCESS_LIMIT`），只读工具（`snapshot`/`read`/`get_html`/`screenshot`/`download`/`wait_for`）与断言工具（`assert_*`/`report_defect`）豁免——多看几眼页面不算打转。`wait` 不豁免：纯睡眠重复没有任何信息量。失败会清零成功计数（流程换了方向）。

### 三、每轮把「当前第几步」顶到模型眼前

6. **进度锚**（`buildStepAnchor`）：`transformContext` 每轮在消息尾部追加一条 `[进度锚] 第 k 轮；用例共 n 步，已自报完成 m 步` + 剩余步骤清单 + 「同一动作重复调用不算推进」。四条硬约束：
   - **只改当次请求，不写回 `state.messages`**。否则 159 轮会累积 159 条几乎相同的进度行，把窗口吃光——它要说的事每轮一样，只有数字在变。
   - **在估算之前并入**。锚就是这一轮真正要发出去的内容，不并进去等于每轮少算一份预算，小窗口下正好够把请求顶过窗口。
   - **增量扫描进度自述**（`anchorScanned` 游标）。每轮全量 `events.join("")` 是 O(n²)。
   - **长度封顶**。清单超 900 字符就退化成「当前步 + 后两步 + 其余见用例原文」；已完成的步骤不再占版面；跑满后不再给清单，只说「输出 `步骤完成：n/n` 并收尾」。
7. **两种进度自述都认**：`parseProgress` 读收尾的 `步骤完成：k/n`，新增 `parseStepMark` 读过程中的「第 k 步完成」。运行中只有后者可用（收尾声明要等全部跑完才出现），两者取较大值，且已完成的步数**只增不减**——模型偶尔先报大数再报小数。

### 四、判定口径：改了对的地方就算做成

8. **替代路径也算恢复**（`unrecoveredToolFailures`）：一次工具失败之后，只要出现过**动作类**工具的成功，就认为它已被另一条路径覆盖。`snapshot`/`read`/`assert_text`/`screenshot` 这类只读调用不能当替代证据——那恰好是「读了一眼没变的旧页面」这种假阳性的来源；导航算动作，换页之后旧失败自然作废。
9. **被中止/未派发的场景必须在报告里显式说明**。没有这句话，「未派发的 16 个场景」与「跑完但没断言的 16 个场景」在 HTML 里完全一样，用户会把「没跑」读成「失败」。

## 后果

- **好处**：按日志估算，权限闸门类 ~10 次 × 省 2 轮 + 遮挡类 ~9 次 × 省 2 轮 ≈ 55–70s，随上游失败消失的熔断空转再省 8 次调用；进度锚负责剩下的部分。预期 **159 轮 → 60–80 轮**，步骤 8/9 不再丢，FAIL 的直接原因消除。
- **代价**：`runAction` 的恢复逻辑从「一处 if」变成一个带 `once()` 的小状态机，可读性下降——换来的是「重试不会变成点两次」这条性质只在一个地方保证。
- **代价**：进度锚每轮多 200–900 字符。这是刻意的：省下的轮次远多于它占的窗口，但它**必须**保持短——已完成的步骤要退出清单，否则 22 步的用例每轮都付全量清单的钱。
- **风险（未验证）**：锚起效的前提是模型遵守「第 k 步完成」的自报约定，而 prompt 早就这么要求了——之前只是没人读、也没人回话。若真机跑出来轮次没降，说明问题更深（模型压根不读尾部 user 消息），那时该改的是注入位置（并入最后一条 toolResult）而不是文案。
- **不改的**：`REPEAT_SUCCESS_LIMIT` 取 3 而不是 2，是因为「点一次确认框再点一次提交」这类动作两连击是正常的；真正的空转在日志里表现为 4–6 次同参重复。
