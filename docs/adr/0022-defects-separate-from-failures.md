# ADR-0022：缺陷与测试失败分离，由模型在运行中上报

- 状态：已采纳 · 日期：2026-10-27
- 相关：ADR-0002（stdout 契约）、ADR-0011（旁路产物）、ADR-0013（场景进程隔离）、ADR-0014（上下文预算）

## 背景

报告目前只有两层：断言与场景结论。断言不成立 → FAIL。「失败」这个词被四件事共用——断言不成立、工具调用未恢复、步骤没跑满、场景异常终止（crash / timeout / infrastructure）。

对提缺陷的人来说，「FAIL」不等于「产品有缺陷」：可能是用例写错了、环境不可用、定位/工具失败、或者模型自己没跑完。把失败直接当成缺陷列给开发，整张清单就没人信。反过来，一条 **PASS** 的用例也可能带着产品问题（console error、接口 5xx 没被断言覆盖），旧报告对此没有任何位置。

## 决策

1. **缺陷 = 被测产品的问题，与「这次测试没跑成」是两件事。** 断言不成立、工具失败、步骤没跑满、异常终止都只是可能发现缺陷的线索，本身不是缺陷。缺陷**不改变** PASS/FAIL 与退出码；PASS 也可以带缺陷，但结论行必须带计数（`结论: PASS（发现 2 个缺陷）`），不能只藏在文末。

2. **缺陷有两个来源。**
   - **模型上报**：运行中新增工具 `report_defect`，字段为标题、严重度（critical / normal / minor）、类型（functional / ui / error / api / performance / other）、期望、实际、证据；场景、用例第 k 步与页面地址（新增 `BskOps.pageUrl()`：桌面端一次 `evaluate location.href`，小程序端读当前页面路由，读不到就留空）由工具自动附带。类型与严重度的英文枚举与 `pass/fail`、`crash/timeout` 同口径，中文只出现在报告层。
   - **确定性兜底**：场景内模型**一条缺陷都没报**时，把**真实断言不成立**补成 `kind: unattributed` 的未归因缺陷（严重度留空、渲染为「未定级」，实际值取断言证据）。合成断言——步骤失败、断言条数不足、工具未恢复——**一律不进兜底**，它们是执行层问题，留在断言表里就够。场景内已有模型缺陷就不再兜底，避免同一次失败被记两遍。

3. **粒度与不可变性。** 一次调用报一条缺陷；同一条断言可对应多条缺陷，多条断言也可对应一条。缺陷只增不改不撤——模型判断错了也留在报告里，轨迹里能看到原因；报告不提供修改入口。

4. **呈现同源。** 文本报告、JSON、HTML 三处用同一份数据。JSON 只在**顶层**写 `defects[]`（套件里每条带 `scenario`），`ScenarioDetail` 不存缺陷；`defects` 为空时不写字段，老报告与老消费方逐字不变。报告顶部放唯一一份汇总，场景节内不重复；单场景报告放在结论之后、断言表之前。

5. **回放共用同一条路径。** 回放没有模型，因此只产出未归因缺陷；不为回放另写一套判定。

## 考虑过的替代方案

- **断言失败即缺陷**：零判断、实现最便宜，但用例写错与环境问题也会被记成缺陷，清单不可提。
- **纯确定性推导**：不新增工具与提示词，但无法区分「产品问题」与「测试问题」，等于给失败换个标题。
- **跑完后单独一次模型调用归纳**：多付一次模型费、重读整份 transcript，而且已经丢失运行时的页面现场。
- **跨场景按标题合并 / 跨运行缺陷库**：合并依赖「是不是同一条」的判断，目前没有确定性依据，猜错会把两个问题压成一个；缺陷跟踪是另一个产品的职责，不该长在测试报告里。

## 后果

- **好处**：报告第一次能回答「这次跑出了什么产品问题」；PASS 带缺陷可见；CI 可直接消费 `defects[]`。
- **代价**：每轮固定前缀多出约 300 token 的工具声明（按现有 21 个工具 ≈6786 token 均摊估算，压缩档把描述压成一行）；缺陷质量取决于模型判断；兜底缺陷没有严重度与类型判断，需要人复核。
- **不变量（有测试钉住）**：`defects` 为空不写字段；PASS 带缺陷时结论行带计数；兜底只来自真实断言失败（合成断言与回放步骤失败断言不参与）；场景内有模型缺陷即不兜底；回放与带模型运行走同一份缺陷判定；缺陷文本全部转义。
