# ADR-0010：交互模式用看板带分列显示场景状态

- 状态：采纳（2026-09）
- 背景：交互模式跑十几分钟、期间还在追加场景时，用户只知道「现在在跑第几条」。状态栏（`updateStatus`）只给一行计数，看不到每个状态各压着几条、哪些待办、哪些已失败。`/status` 能打出全量列表，但它一次性刷过去、不常驻。因此加一块**常驻的看板带**：把场景按状态分成 5 列，实时跟着队列变。

## 决策一：看板带与日志视口共存，不取代日志

看板带放在日志视口**上方**，日志视口缩小继续流式刷新（布局根：`VStack([kanban, transcript, dock])`）。

理由：那片滚动日志是整个 TUI 里**唯一能看见「正在跑的场景卡在哪一步」的现场**——bsk 命令、每轮 LLM 调用、步骤耗时都从 stdio 重定向进这里（`app.ts` 的 `setSink`）。把整片换成看板，长流程调试时会看不见「卡在哪一跳」。共存让看板给总览、日志给现场，信息密度最高且不丢现场。

## 决策二：5 列，不是用户最初说的 4 列

列为 `等待中 / 进行中 / 成功 / 失败 / 已取消`，与内核 `ScenarioState`（`queued | running | pass | fail | cancelled`）一一对应。

理由：用户最初只列了前 4 列，但 `已取消` 是领域术语表定义的一等终态——「既不是通过也不是失败，不计入退出码，也不写入回放脚本」（`CONTEXT.md`）。`/cancel`、Esc 中止、模型探活失败都会产生它，CI 退出码判定依赖「取消 ≠ 失败」这条边界。漏掉这一列会把「用户主动中止 / 模型连不上」误读成「用例失败」。

## 决策三：终端太窄时不渲染看板，整片留给日志

`KANBAN_MIN_WIDTH = 90`：终端列数低于此值，看板带清空（高度退为 0），全部空间让回日志视口。

理由：pi-tui 的 `ScrollView` 只支持纵向、**没有横向滚动**，横向溢出只能自己截断或平移。5 列要横向铺开，每列至少约 16 显示列（CJK 列名 + 卡名截断）≈ 90 列才够看；窄屏（被拖小的面板、80 列 SSH）硬挤只会互相覆盖，反而没法用。看板是交互模式的锦上添花，不是唯一信息源——窄屏退回纯日志是最稳的兜底。

## 决策四：看板带固定高度、不滚动；溢出用 `+N 更多` 收尾

每列只放得下的最近若干张（高度随终端行数自适应 2~7 行），多了显示 `… +N 更多`。全量列表永远在 `/status` 与日志里。

理由：若让某一列能独立滚动，会和既有的键位契约打架——`tests/tui.test.mjs` 钉死 `↑/↓` 在输入框为空时**必须归日志视口**（`arrowKeysBelongToLog`）。不引入列内滚动，这条契约零改动。看板定位是「总览」而非「全量列表」。

## 决策五：看板是纯展示，点击不做任何操作

鼠标点击看板不取消 / 不中止任何场景；取消待办仍走 `/cancel <n>`、中止进行中仍走 `Esc`。

理由：破坏性操作不该藏在鼠标点击里——误点一下就取消一条「已提交但没跑」的场景，等于抽掉「提交了就一定会跑」的承诺。先稳住视觉，交互留待后续。

## 决策六：看板纯增量，不动状态栏与 `/status`

状态栏（运行中计数、模型、落点、用量）与 `/status` 命令原样保留；看板只负责可视化分列，三者互补不替代。

理由：改动面最小、不破坏既有行为与测试；看板是「锦上添花」而非重构。

## 决策七：配色复用现有主题，状态一眼可辨

`等待中`=dim（灰）、`进行中`=accent（高亮）、`成功`=ok（绿）、`失败`=err（红）、`已取消`=warn（黄）。列头带该列场景数。

理由：复用 `src/tui/theme.ts` 现有着色函数，与报告 / `statusTag` 的语义色一致，不新引入调色板。

## 实现要点

- 看板带是一个 `Text`，内容在 `renderKanban()` 里按当前队列**现算现画**：每列按显示宽度用 `truncateToWidth`（`pad=true` 的 `padToWidth` 补空格对齐，CJK 占 2 宽），列间用 `dim("│")` 分隔；`setText` 进 `kanban`，由 `updateStatus()`（状态变化 + 1s ticker）驱动刷新。「进行中」卡尾部追加实时耗时（`fmtDuration(Date.now() - startedAt)`），因此会随 ticker 跳动。
- 列内按 `id` 升序（提交顺序），与队列顺序一致。
- 终端尺寸在 `tui.start()` 之后才就绪，故启动后额外调一次 `updateStatus()` 渲染首帧；之后每 1s ticker 自愈（含 resize）。

## 未采纳的方案

- **看板取代日志视口**：丢现场，见决策一。
- **4 列（漏掉已取消）**：模糊 CI 退出码语义，见决策二。
- **窄屏下把 5 列竖向堆叠成单栏列表**：牺牲「看板」形态，且仍要处理 CJK 宽度；不如直接退回纯日志。
- **窄屏下压到最小宽度 + 狠截断卡名**：信息失真（可能只剩 `#3 成…`），不如整片日志。
- **列内独立滚动 + 改键位让某一列可滚**：破坏 `↑/↓` 归日志的测试契约，见决策四。
- **点击卡即取消 / 中止**：破坏性操作藏在点击里，见决策五。

## 影响

- 新增 `KANBAN_MIN_WIDTH` 常量与 `padToWidth` / `renderKanban()`（`src/tui/app.ts`）。
- 布局根 `VStack` 增加 `kanban` 一格（`basis:0, grow:0, shrink:1, minSize:0`，保证窄屏时高度退 0 把空间让回日志）。
- `updateStatus()` 末尾追加 `renderKanban()`；`tui.start()` 之后补一次 `updateStatus()`。
- `src/i18n.ts`：新增 `tui.kanban.waiting/running/pass/fail/more`（zh + en）；已取消列标题复用 `common.cancelled`。
- 测试：`tests/tui.test.mjs` 不受影响（未碰键位 / `arrowKeysBelongToLog` / 报告 / 队列语义）。
- 文档：`CONTEXT.md` 补「看板带」术语。
