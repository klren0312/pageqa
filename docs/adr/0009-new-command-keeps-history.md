# ADR-0009：`/new` 开新会话，但已跑过的场景不许丢

- 状态：采纳（2026-09）
- 背景：交互模式跑久了，视口与运行队列都在累积（十几分钟的日志、几条已结束的场景）。想换一个任务重新开始时，此前只能 Ctrl+C 退出再重开——而重开丢掉的是整个会话状态：`/model` 选的模型、`/run` 定的落点、token 计数。因此加 `/new`：**在当前进程里开一个新会话**。

## 决策一：清掉的是视口与运行队列，不是历史

`/new` 先把当前一批快照进 `batches`（`snapshotBatch`），退出时的汇总报告与回放脚本再把归档批次与当前批次合并（`combineBatches`）。

理由：静默丢数据的后果很具体——报告里少几条，而 `--emit-script` 会产出一份**看起来完整、实际缺场景**的回放脚本，比不写更危险（与 ADR-0005 决策七同一条理由）。而且用户可能在上一批里已经等了十几分钟，那些结论不该因为「清了屏」而消失。

## 决策二：队列里还有在跑或待办的场景时拒绝执行

报错并给出两条出路：正在跑的用 `Esc` 中止，待办的用 `/cancel <n>` 取消（或者用 `Ctrl+C` 收工，那条路本来就会取消全部待办并说清楚）。

理由：ADR-0002 决策五承诺「提交了就一定会跑」。`/new` 直接清队列会**静默**违背这条承诺——被取消的场景连一行日志都留不下。与其偷偷取消，不如让用户明确处理。

## 决策三：落点（写回目标）不跟着换

静默丢掉落点，会让之后敲下的用例不再写回文件，而用户以为「敲下去就等于留下了」——这是最难发现的一类意外（ADR-0005 决策六处理的就是这个状态）。想换用例文件本来就有 `/run`，它会把落点一并带过去。

## 决策四：先把上一批的归档小结写进新视口，再清空显示

`/new` 之后新视口开头是：一行 banner（上一批 n 个场景 · 通过/失败/已取消）+ 每个场景一行（编号、结论、来源）+ 一行说明（清空了哪些、什么被保留）+ 一行落点提示。顺序必须是「先算好内容再清屏」，反了就把刚要写下的东西自己擦掉。

理由：清屏之后用户就翻不回上一批的结论了；把最重要的一屏摘要留在新会话开头，比让他去翻（已经不存在的）历史更诚实。

## 决策五：token 计数归零，进程级写回计数保持累计

token 计数由 `results` 派生，`/new` 清空 `results` 后自然从头开始——「本次会话消耗了多少」正是用户要看的量。而「已写回 N 个场景」是**进程级**事实，退出时要如实报出这个进程一共写了多少，因此不重置。

## 未采纳的方案

- **`/new` 顺手取消待办并继续**：静默违背「提交了就一定会跑」，见决策二。
- **`/new` 连落点一起清**：见决策三。
- **`/new` 真的丢掉上一批（彻底全新开始）**：报告与脚本会缺场景；用户已经为那些场景等过时间，丢掉的代价由他承担、收益却没有。
- **退出进程再重开一个**：丢掉模型选择、落点与 token 计数——而那正是 `/new` 想避免的。
- **`/new --force` 强制清空**：多一个开关就多一种「我到底清掉了什么」的犹豫；要收工用 `Ctrl+C`，它已经能取消全部待办并留下记录。

## 影响

- 新增 `src/tui/batches.ts`：`snapshotBatch()` / `combineBatches()`（纯函数，输入是队列项与结果表，因此「归档不丢数据」可直接单测）。
- `src/tui/app.ts`：场景执行器抽成具名 `runScenario`；`queue` 由 `const` 改 `let`（`/new` 要换一条新队列，所有引用点读到最新那条）；新增 `newSession()` 与 `/new` 命令；退出时的报告组装改用「归档批次 + 当前批次」。
- `src/i18n.ts`：`/new` 的 banner、归档说明、落点提示、两种拒绝理由，以及 `/help` 与未知命令列表里的条目。
- 测试：`tests/tui.test.mjs` 新增 4 条（快照内容、未运行场景如实标注、已取消不进录制、跨批次合并且顺序稳定）。
- 文档：README 两个语种的命令列表与要点。
