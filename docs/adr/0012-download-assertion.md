# ADR-0012：下载断言——真值只认「捕获到 + 落盘」，超时是 FAIL 不是跳过

- 状态：采纳（2026-09）
- 背景：用例里「点击导出，确认后应该有文件下载下来」这类步骤此前**无法判定**——断言工具只有 `assert_text`（读页面文本），而下载不改变页面文本。于是用例只能写成「浏览器出现下载记录或页面出现成功提示」，落到报告里是一句靠模型自述的弱断言；回放时更是完全无法校验（零模型回放不能读浏览器下载栏）。bsk 早在 CLI 层就有 `download` 子命令（`bsk download <ref> --out <path>`：由它自己点击触发元素、捕获一次下载并落盘，`--json` 回传 `suggested_filename` / `byte_size` / `mime` / `danger`），缺的只是 pageqa 没把它接出来。

## 决策一：`download` 是动作型工具，同时本身就是一条断言

新增第 10 个工具 `download(target, expectName?, out?, timeoutMs?)`：`target` 是**触发下载的元素**（导出按钮，或确认弹框里的「确定」按钮），由工具自己点击并捕获。工具返回结构化结果（`AssertOutcome`：期望 + 成立与否 + 证据），与 `assert_text` 走同一条上报链路，因此断言会进 `assertions`、进文本/JSON/HTML 报告、影响退出码。

理由：

- **形状对齐 `upload`**：两者都由工具自己点触发元素（`upload <ref> --file` ↔ `download <ref> --out`），模型已经会的模式不必再学一套。
- **不先 `click` 再捕获**：实测 bsk 的 `download` **要求 target**（省略直接 `missing target`，`exit_code` 2），并不存在「等一次正在进行的下载」这种用法。先 click 会让那次下载流走、没人接，随后必然报「没捕获到下载」。这条约定写进了系统提示。
- **不做「纯落盘动作 + 另写断言」**：「下载成功了没有」本身就是确定事实（捕获到/没捕获到），把它交给模型用另一句话去断言，等于把确定性结论重新泡回语言里。

## 决策二：判定口径 = 捕获到一次下载 + 文件落盘非空（+ 可选文件名通配）

成立条件只有三条，按顺序：捕获到一次下载；文件真的在本地且字节数 > 0；若用例给了 `expectName`（通配，支持 `*`/`?`，大小写不敏感，不带通配符即全等），文件名要匹配。

**不校验文件内容**：解析 xlsx/CSV 校验行数是导出方自己的事，pageqa 越过页面去解业务格式，只会把「文件下载了」这条断言和「导出内容对不对」这条业务断言绑死在一起——后者应该由页面上的业务断言承担。

`expectName` 同时比对**落盘名**与**服务器建议名**：写用例的人通常只关心「名字里含某段文字」（`*报表*`）或「后缀对不对」（`*.xls`），两者都匹配；写死完整名（如 `导出报表.xls`）在落盘名上会因多了时间戳前缀而对不上，只有建议名（服务器给的原名）能对上。

## 决策三：失败分三类，「元素点不到」抛错，「点了没下载」记 FAIL

| 情形 | 处置 | 理由 |
| --- | --- | --- |
| 触发元素点不到（选择器错、`@eN` 失效、session 掉了） | **抛工具错误**（模型重新 snapshot 后重试） | 这一步**根本没走成**，不等于「下载没发生」。记成不成立断言会把模型的一次笔误变成假用例失败；普通动作遇到同样问题也是抛错重试 |
| 元素点到了，等待期内没有产生下载 | **工具内先重试一次**（再点一次、再等一个 `timeoutMs`），两次都没等到才记**不成立的断言** | 实测 bsk 的下载捕获有「冷启动」特性：daemon/浏览器刚重启（或刚升级）后的**第一次捕获必然失败**，同一元素紧接着第二次就成功。而「没捕获到」按设计是洗不掉的 FAIL，不重试就等于让这个抖动直接当结论 |
| 落盘失败 / 文件 0 字节 / 文件名不符期望 | **不成立的断言**，证据带真实路径与真实文件名 | 同上；已落盘的仍算「下载产物」，摘要里照样报出来 |

`timeoutMs` 默认 **60s**（不沿用 bsk 自己的 2 分钟）：导出接口常是服务端现生成文件，几十秒很正常，但 2 分钟对「点了没反应」的排查太长了；用例写更长的等待就显式传 `timeoutMs`。

**为什么下载要重试而其它动作不重试**：其它动作「点不到元素」会抛错、由模型重新 snapshot 后自己重试；而下载的「没等到」被设计成**结论**（断言不成立），结论一旦写下就洗不掉——模型后面再点成功，报告里那条 FAIL 还在。所以这一类的抖动必须在**工具内**消化：同一个元素、同样的等待上限，最多点 2 次（`DOWNLOAD_ATTEMPTS`），重试过程打一行日志，成功后的证据里注明「首次未被捕获，重试后成功」。代价是「真的没下载」的场景最坏等 2×`timeoutMs`。

两次都没等到时，如果 bsk 的信封是 `download_capture_failed`（它认得这一类），证据里追加一句可执行的下一步——**翻译，不猜测**：这多半是捕获尚未就绪（重连扩展/稍后再试），而不是被测页面有问题；只报「点了没产生下载」会把人引到错误的排查方向。这一句是实测踩出来的：daemon 从 0.3.0 自动升级到 0.3.1 的那段时间里，连重试也一起失败，而升级前同样的操作是成功的。

区分「元素点不到」与「没等到下载」靠 bsk 打在 **stdout** 的结构化错误信封（`{"code":"not_found","message":…}`）。为此 `runBsk` 把 stdout/stderr 贴到错误对象上再抛——`execFile` 回调里的 `error` 上**不带**这两条流（实测 Node 22 上 `err.stdout` 就是 undefined），原样 reject 的话上层只剩一行 `Command failed: bsk …`，navigate 诊断与下载证据都吃这个亏。

## 决策四：落盘路径 = 显式原样 / 默认「下载目录 + 时间戳 + 服务器建议名」

- **用例显式给了 `out`** → 原样使用（相对路径按 cwd 解析），**不加时间戳前缀**，并给 bsk 传 `--overwrite`：用例点名了「就写到这个文件」，第二次运行因文件已存在而失败会被读成「下载坏了」。
- **没给** → `<下载目录>/<yyyyMMdd-HHmmss>-<服务器建议名>`，默认下载目录 `~/.pageqa/downloads`（`config.downloadDir` 可覆盖，键缺失即默认，理由同 ADR-0011 决策一）。与 HTML 报告「文件名带时间戳、多次运行互不覆盖」是同一套做法——一次运行一次证据。
- **必须先落临时名再改名**：bsk 要求先给 `--out` 才能开始捕获，而「服务器建议名」只有捕获完才知道。临时文件与最终文件同目录，改名是同卷操作；改名失败就保留临时名并在证据里给出真实路径（留着总比丢掉这次捕获强）。
- **服务器给的文件名是外部输入**：按路径分隔符/Windows 保留字符/控制字符清洗，去掉首尾点与空格，截断到 120 字符，清空则退回 `download`——不清洗就是拿 `Content-Disposition` 直接拼路径。
- 同秒同名时退让为 `-2`/`-3`（bsk 默认拒绝覆盖已存在文件，撞名会让第二次捕获直接失败）。

## 决策五：捕获到的文件进「本次产物清单」，且**没有「生不生成」的开关**

收尾清单（stderr，见 ADR-0011 决策五）在报告与脚本之后，每个捕获到的文件列一行 `下载产物: <绝对路径>`。报告里的路径是「事后可查」，而用户最想知道「文件在哪」的时刻是运行刚结束那一刻。

不设「生不生成」的开关：它不是「本次生不生成」（报告/脚本那种可由偏好决定的东西），而是「用例有没有下载文件」——关掉开关并不会让文件不存在，只会让人找不到它。只有真的收了文件才列，不打印「下载产物: 无」。

## 决策六：零模型回放支持 `download` 步骤；下载失败**不按「元素未找到」跳过**

回放脚本新增步骤类型 `download`（`target` + `locator` + 可选 `out`/`expectName`/`timeoutMs`）。脚本只记**用例真的写过**的 `timeoutMs`：写死一个默认值会让「将来改默认」失效。

- 触发元素用语义定位符在**回放时的新快照**里重新解析（同其它步骤）。
- **触发元素找不到 → FAIL 断言，不按「元素未找到」跳过**：普通动作的 skip 规则（ADR 里 `LocatorMissError` 的那条）针对的是「录制期模型顺手点的补救动作，回放时页面更顺、按钮不存在了」；下载步骤承载断言，跳过它等于把「该下载却没下载」洗成通过。假通过比报错危险得多。
- 「没等到下载」在**工具内**最多点 2 次（首次被时序吞掉时重试一次，见决策三），回放与带模型跑同一条规则；除此之外的失败是**不成立的断言**而不是抛错，因此不会被 `runStepWithRetry` 再叠加重试（那会点更多次导出按钮、产生多个文件）；只有意外的执行错误（如目录不可写）才走既有重试。

## 决策七：断言**成立后清理**文件，且**在场景收尾时**统一删

默认（配置 `downloadCleanup` 缺失即视为开）：**断言成立且用的是默认落盘路径**时，捕获到的文件被登记为**待清理**，在该**场景收尾**时一次性删除（带模型跑与零模型回放同一条规则：`agent.ts` 的场景收尾、`replay.ts` 的 `finally`）；三条例外一律保留：

- 用例**显式给了 `out`** → 保留：那是用户点名要的文件，工具没资格替他删；
- 断言**不成立**（没等到下载除外，那种情况压根没文件；命中「文件名不符」「0 字节」时有文件）→ 保留：失败时的文件正是排查对象；
- 配置把 `downloadCleanup` 设为 `false` → 保留：他要留档。

为什么默认清理：回归跑一百次就堆一百个文件，而**通过的用例没人会去看那些文件**；要留档的场景（人工验收、要交付文件）本来就会显式给 `out`。

**为什么不在捕获成功后立刻删**（早期实现就是这样，实测踩了）：同一个场景里，这个文件**后面还可能被用到**——后面还有步骤/断言要碰它，人也可能想在场景跑完前看一眼。当时是「捕获 → 立即删 → 再写结论」，于是出现「明明下载成功了，文件却已经没了」。移到收尾删：文件在整个场景期间都在，运行结束时目录依然是干净的；代价是被强杀（Ctrl+C 硬退、进程被 kill）时可能留下待清理的文件，这是可接受的（文件可见、路径也在清单里）。

清理必须**如实标注**，但不撒谎的顺序是「先计划、后事实」：捕获时的证据只说明**按规则会在本次运行收尾时清理**；而 `下载产物: <path>（断言成立后已清理）` 只由**真的删掉了**才标（删失败就不标，说明文件还在原处）。

## 未采纳的方案

- **靠页面成功提示（toast）当断言**：不用加工具，但提示文案由被测系统决定、回放时还会变，且「提示成功但文件没下来」才是真正要抓的缺陷。这是本 ADR 要替换掉的做法。
- **校验文件内容（解析 xlsx 行数 > 0）**：见决策二。
- **用浏览器默认下载目录**：pageqa 未必知道它在哪，且会污染用户自己的下载历史；默认目录放在 `~/.pageqa/downloads` 也与 `pageqa-report/` 的口径一致。
- **回放时覆盖同一个文件名**：不堆积，但会吃掉上一次的证据，而下载文件**不可重建**（回放脚本可以重建，所以它才敢覆盖同名）。
- **按时间清理下载目录里过期的文件**（如「保留最近 N 份」）：等于定期在用户目录里自动删文件，判据也不靠谱（哪些是本次的？哪些是用户自己放的？）。改成**按结论清理**（决策七）：清什么，由这一次运行的结论决定。
- **捕获成功后立刻删文件**：见决策七——同一场景里后面的步骤/断言可能还要用这个文件，删早了会出现「下载成功了、文件却已经没了」。
- **只观察不落盘**（避免产生文件）：bsk 的 `download` 必须给 `--out`；而且「文件真在本地」是这条断言最有力的证据。
- **给 bsk 上游提需求**：它的 `download` 已经够用（`suggested_filename`/`byte_size`/`mime` 都给到了），问题只在 pageqa 这侧的接线。
- **一次点击捕获多个文件**：bsk 一次只捕获一次下载；多文件场景不进这一版。
