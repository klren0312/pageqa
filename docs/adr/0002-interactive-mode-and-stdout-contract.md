# 交互模式用 pi-tui，且「stdout 只放报告」这条契约只在批处理模式成立

状态：accepted

长流程单次可能跑十几分钟，而这期间无法追加用例：想补一条只能干等，或者杀掉重来。因此 pageqa 增加**交互模式**——场景执行期间仍可提交追加场景。界面层采用 `@earendil-works/pi-tui`（`TuiAltScreen`）。

## 决策一：用 pi-tui，不用 readline

「上方持续滚动的日志 + 底部固定输入框 + 执行期间可输入」是 pi-tui 的一等公民布局（`VStack([ScrollView(follow:"end"), dock])`，pi 自己的 coding-agent 用的就是这套）。不用 `node:readline` 手搓的理由是它会连着带出四件事：光标重绘、窗口 resize、与异步日志互相打架的 prompt、以及中文输入法的候选窗定位（pi-tui 用 `Focusable` + `CURSOR_MARKER` 把硬件光标钉到输入点，这是 readline 给不了的）。

代价已在选型时确认：`engines` 抬到 `node >=22.19.0`；库**不导出任何默认主题对象**，`EditorTheme`/`MarkdownTheme` 必须自持一份（16 色默认，`COLORTERM` 含 `truecolor`/`24bit` 才升级）；raw mode 下 Ctrl+C 不再触发 SIGINT，退出由我们自己拦。

## 决策二：用 `TuiAltScreen`，放弃内联 scrollback

`TuiMainScreen` 能保留终端 scrollback，但**当改动出现在视口上方时会触发清屏 + 清 scrollback 的全量重绘**（`tui-main-screen.ts:451-455`）——十几分钟持续追加日志正撞在这个弱点上。`TuiAltScreen` 由应用自管滚动，上万行 transcript 也不触发全量重绘；代价是放弃内联 scrollback，退出时由我们主动把最终文档打到主屏——这恰好和「退出后回到批处理口径」吻合。

## 决策三：交互模式由 TTY 自动识别，`--no-tui` 作逃生舱

判据是 `stdin.isTTY && stdout.isTTY`——**必须同时看 stdin**：TUI 要 raw stdin，只看 stdout 会让 `pageqa case.md < /dev/null`、IDE 内嵌终端、CI 子 shell 进去一个收不到键的空壳。

- 阻止项：`--json`（机器消费方要纯 stdout）、`--replay`（秒级零模型，全屏只是噪音）、`--session`（见决策四）。
- `--out` **不阻止**：它的语义是「报告另存一份」，与要不要看 TUI 无关；把它设成阻止项会逼人为了存个报告放弃交互。
- `--no-tui`（并认 `PAGEQA_NO_TUI=1`）给「本机就想看滚动日志」与排障用。
- 显式 `--tui` 但非 TTY 时**直接报错**，不静默降级——静默降级会让人以为 TUI 坏了。

这里刻意偏离了「交互是大改动，该用显式 flag 开关」这条常规做法：批处理与交互的差别被压缩到「有没有 TTY」，是因为它本来就是「人看不看这个终端」的同义词。风险由 `--no-tui` 与三条阻止项兜住，并且 `tests/smoke.test.mjs` 走管道 stdio（`stdin.isTTY` 为 undefined）会**自动降级**，现有端到端测试不受影响。

## 决策四：`--session` 在交互模式下禁用

`--session <id>` 现有语义是「指定一个已存在的 session 给这次运行用，跑完也关掉它」。但交互模式串行 N 个场景 = N 个 session，一个 id 不够分。让 `--session` 只作用于第一个场景、或让所有场景挤同一个 session，都是在给「场景拥有独立的 bsk session 与浏览器窗口」这条不变量开洞，而且很难向用户解释。因此：交互模式下用了 `--session` 直接报错。批处理模式行为完全不变。

同理，排队中的场景**执行时才创建**自己的 session：提交时就建会让终端背后冒出一堆空窗口，用户会以为任务已经开始跑了。

## 决策五：中断的场景是「已取消」，不是「失败」

`Agent.abort()` 是 pi-agent-core 唯一的中断途径，它的行为很脏：`waitForIdle()` 照常 resolve（不 reject）、`state.errorMessage` 被设成中止文本、**并在 `state.messages` 里留下一条空的/半截的 assistant 消息**（`stopReason: "aborted"`，见 `agent.ts` 的 `handleRunFailure`）。而 `finalizeResult` 一看 `errorMessage` 就无条件往报告塞 FAIL 断言，所以「什么都不做」的结果是中断自动变成失败。

按 Esc 是「我不想再等这个了」，不是「这个用例失败了」。记成 FAIL 会让退出码与报告说谎，还会把半截轨迹录进回放脚本。因此引入第三种终态「已取消」：不进 PASS/FAIL、不计入退出码、**不写入回放脚本**（与 ADR-0001「假通过比报错危险得多」同一条理由——写进去会让 `--replay` 跑半个用例还可能报 PASS）。中止后仍必须关掉该场景的 session 与窗口（现有 `finally` 已保证），并在视口里明说「剩余步骤未执行」。

注意与决策七的区别：**追加场景计入脚本，已取消的场景不计入**——脚本只收「真的跑过」的场景。

队列语义同步确定：支持取消**未开始**的场景（`/cancel`），一个场景结束（通过／失败／已取消）后**自动开始下一个待办**——「提交了就一定会跑」才是队列的承诺。

## 决策六：追加场景的占位符与初始场景共用同一时刻

`vars.ts` 的既有规则是「同一次运行内所有占位符共用同一时刻」，回放脚本靠 `recordedValue → 占位符` 反查还原。若追加场景（可能晚十分钟提交）各用自己的时刻，同一份脚本里 `${timestamp}` 会对应多个不同的录制取值，反查变得含糊，而「同一次回放共用一个时刻」又要求它们必须能统一展开。

代价是十分钟后追加的用例名字里带的是十分钟前的时间戳——但时间戳的作用本来就是「不重名」，不是「记录真实时刻」。

## 决策七：追加场景计入回放脚本，并写回源用例文件

回放脚本是「源用例文件被跑通一次后的固化产物」，它的自足性来自「脚本 + 源文件 + 漂移检测」三件套。因此追加场景不是只进报告，而是**落点补齐**：提交时以 `## <场景名>` + 用例原文追加进源用例文件，并与初始场景同等地录入回放脚本。

这也顺带闭合了一个缺口：`source.hash` 的漂移检测此前只能覆盖初始文件，追加场景的原文不在其中（等于「追加场景永远不会提示过期」）。写回之后 hash 覆盖的就是全部场景，不必给脚本加逐场景 `caseText`。

**场景名由用户定**：输入框里写了 `## <标题>` 就用它（与初始用例文件的写法完全一致），没写才退回首行摘要（截断 40 字符）。这不是 UI 措辞问题：标题会永久写进用户的用例文件，而「文件里的标题由文件的主人决定」是 `examples/*.md` 一直遵守的规则；UI 替用户命名只是因为我们没给入口，给个入口更诚实。

同理，**重名时也不改写用户给的标题**：`splitScenarios` 本来就不要求场景名唯一，序号只用于视口与报告里消歧（报告里仍是「场景 2：登录测试」这种带序号的呈现），文件里写什么就是用户写什么。

三条硬约束（正确性问题，不是取舍）：

1. 写回的是**用户输入的原文**（含 `${timestamp}` 占位符），绝不写展开后的具体值——否则下次运行必撞名，等于把一次性用例写进文件。
2. 用 `appendFile`，**不重写整个文件**——用户可能同时在编辑器里开着它，重写的破坏面大得多。
3. 写回格式与 `splitScenarios` 的解析规则严格对齐，写回去再用同一条规则读回来必须一模一样。

**时机是提交即落盘**：敲下来的就是用户要留下的用例；跑完才写会让 Ctrl+C 或崩溃把整条待办队列丢掉，而「不想丢掉想跑的用例」正是交互模式存在的理由。**已取消的场景留在文件里**（它仍是用户写下的合法用例，取消的只是这次执行），但**不进脚本**——与决策五同一口径。

**必须连带修的一处**：`source.hash` 目前来自**启动时读到的** `sourceText`（`src/index.ts:355` → `buildReplayScript`）。写回之后文件内容已变，沿用启动时那份会让**第一次回放就报「源用例已变更」**。生成脚本前必须重新读取源文件并据此算 hash。

**交互模式因此要求必须有源用例文件**：`pageqa --tui "<内联文本>"` 直接报错。这与仓库既有的脾气一致——宁可直接报错，也不静默降级、不在用户工作目录里凭空造文件。退出时打印「已写回 N 个场景到 `<file>`」，README 里提醒交互模式会改动源用例文件。

## 考虑过的其他方案

- **用 `node:readline` + 现有 stderr 滚动日志，只把输入接到队列上**：改动最小，但要手搓光标重绘、resize、IME 与「日志和 prompt 互相打架」，在中文输入法与 Windows 上尤其容易翻车。
- **显式 `pageqa --tui` 开关**：语义最干净，但日常使用要么记着加 flag，要么在一个「看起来能交互但实际不会」的终端里等半天。选自动识别 + 逃生舱。
- **`TuiMainScreen` 内联渲染**：保住 scrollback，代价是长 transcript 加视口上方改动时的全量重绘。
- **把新输入追加进正在跑的场景**：正在跑的场景其用例文本早已 `numberSteps` 编号后 prompt 进 agent 上下文，中途插步骤模型看不到、编号会错位。声称支持就是骗人，因此输入只能产生新的场景。
- **中止即停整个 TUI（连队列一起放弃）**：中止一个不等于要放弃另外五个。
- **交互模式下跑到一半就落盘 `--emit-script`**：会产出「看起来完整、实际缺场景」的脚本，比不写更危险。改为退出时一次性写入。
- **追加场景不进回放脚本**（只参与本次运行与报告）：一度考虑过，理由是「没有源文件、无法参与漂移检测」。改为写回源用例文件后这条理由消失——追加场景有了自己的落点，脚本与源文件重新一一对应。
- **写回时把已取消的场景从文件里撤销**：需要去改一个用户可能同时在编辑器里编辑的文件，互相覆盖的风险远大于收益；而且「这次不跑」不等于「这条用例不要了」，下次还能跑。
- **给写回加 `--no-write-back` 开关**：多一个开关就多一种需要解释的状态。「交互模式会追加源用例文件」应当是预期行为，靠文档与退出时的提示说清楚即可。

## 补充（2026-09，见 ADR-0011）：旁路产物落盘不算 stdout 输出

测试报告（`pageqa-report/`）与回放脚本都是**旁路产物**：默认生成、可在 `/setting` 里关掉、路径只经 `info()`（stderr / TUI 视口）告知，绝不进 stdout。这与决策三里 `--out` 的处理是同一条：**「另存一份」不改变 stdout 的契约**。
