# ADR-0013：场景在独立子进程中执行，父进程串行编排并汇总

- 状态：采纳（2026-09）
- 背景：场景之间原本只隔着「独立 bsk session 与浏览器窗口」，但它们跑在**同一个 Node 进程**里。一次原生崩溃（浏览器/daemon 把进程带崩、OOM 被系统杀掉）会带走整个队列——后面还没跑的、已经跑完只差汇总的，一起没。同时也没法「只重跑失败的那一个」，只能把整份用例重跑一遍。
- 事实：
  1. 一次 CLI 调用里所有场景跑在同一个进程：`runSuite` 是 `for…await` 逐个 `runAgent`；交互模式的 `ScenarioQueue.pump()` 同样一次只跑一个（`src/agent.ts`、`src/tui/queue.ts`）。
  2. bsk 工具层的「一次只有一条命令在飞」是**模块级 Promise 链**（`commandChain`），**只在本进程内有效**；跨进程没有互斥，也没有任何机制协调。
  3. 每个场景各自建 session、在 `runAgent` 的 `finally` 里关。进程被强杀时，session 与它的浏览器窗口**无人收尾**。
  4. 崩溃与超时的原因在报告里**无处可写**：`TestReport.scenarios[]` 里只有 `summary`（人读），没有机器可读的分类字段。

## 决策一：隔离的边界是一次进程边界

每个场景都在与父进程分离的子进程中执行；父进程仍按运行队列**串行** fork。`--only <序号|精确标题>` 是子进程的入口。

理由：进程内拦不住原生崩溃。子进程是唯一能真正做到「崩一个不影响别人」的边界。

## 决策二：`--only` 是唯一的地基，父进程复用它

父进程 fork 用的就是公开入口，没有第二套通道：

```
pageqa --only <序号|精确标题> --json <用例文件> --session <id> --no-side-outputs
```

「单独重跑一个场景」与「父进程的内部隔离」是同一段代码。标识收序号与精确标题两种（非纯数字按标题**精确**匹配，匹配不到则报错并列出候选）；模糊匹配是 `/run <关键词>` 的职责，两者语义不混。

## 决策三：默认串行，`--concurrency` 显式开并行（推翻最初「串行，不并行」）

最初这一条写的是「即使每个场景是独立进程，也不并行」，理由是「bsk 的串行锁是 per-process 的，跨进程并行会击穿它」。**这条理由是错的**：那个锁本来就是模块级的，只保证**本进程内**的命令不互相并发；跨进程时由 daemon 自己仲裁，而每条 bsk 命令本来就带 `--session`、按会话隔离。场景搬进子进程之后，它恰好不再是障碍——进程隔离正是并行的前提。

改成「并发是一个**上限**」（`--concurrency <n>`；`PAGEQA_CONCURRENCY` 与配置文件里的 `concurrency` 也可以给；**默认 1**）：

- **默认 1（逐个跑）**：串行是「场景之间可能有隐含顺序依赖」的默认保护——「创建 → 编辑 → 删除」并行跑不是失败，是数据错乱，而且更难查。并行等于声明「这些场景互不依赖」，这个声明只能由人来做，工具猜不出来。
- **上限 8，超过直接报错**（不做静默截断：说 16 却只跑 8，比报错更难查）。并发的代价是同时开着同样多的浏览器窗口。
- **批处理与交互模式都认它**：`--concurrency` 启动时对两者都生效，交互模式进去之后还能用 `/setting` 里的「并发量」随时改（档位 1/2/3/4/6/8）。改完**立刻生效**——队列每一轮派发前现取，所以在跑的场景不受打扰、之后派发的按新值来——并写回配置。`--replay` 根本不走调度器，显式与它同用会报错，而不是静默二选一。
- **交互模式的并发语义**（并发之后「当前场景」不再唯一，这几处必须跟着改）：看板带的「进行中」列本来就能挂多张卡（按状态过滤 + 各自实时耗时），不用动；状态栏那句「第 k/n 个」换成「运行中 N 个 · 最早…已跑 …」；实时 token 用量从「单值」改成按场景记的 Map，否则会话累计会漏掉除第一条以外的场景；`Esc` 一次中止**全部**在跑的场景（逐个停会让人以为按了没反应），被中止的逐个点名。
- **并发只改变「什么时候跑」，不改变「结果按什么顺序排」**：报告里的场景顺序、合并出来的回放脚本顺序都仍按用例原文——谁先跑完不影响。这是并行不该改变的东西，用调度器的「按原始下标归位」保证。
- **并发时日志必然交错**，所以只有这时给每行加 `[场景名]` 前缀（决策九的原话是「不加前缀」，而那条的前提正是「场景串行、顺序足以分辨」；前提没了，做法就得跟着变）。

## 决策四：父进程持有 session 的生命周期

父进程在**轮到该场景时**创建它的 bsk session，用 `--session <id>` 传给子进程；子进程被中止、崩溃或超时后，由仍然活着的父进程 `session close`——关 session 会连带销毁它的 Agent Window，孤儿窗口一并解决。

理由：让子进程把 session id 上报给父进程，在最需要它的时候（崩溃、被强杀）恰好不可靠——还没上报就没了。此处「轮到它时才创建自己的 session」的**时机**与**一对一归属**都没变，只是创建者从子进程变成父进程。

## 决策五：子进程恒定输出套件形态，父进程只消费 stdout

子进程哪怕只有一个场景，也输出带 `scenarios[]` 的报告；父进程只读它的 stdout JSON，不发明新的进程间协议。

理由：汇总只有一条输入路径，不必维护「单场景报告 → 套件成员」的归一化分支；且 `--only` 单独跑与内部 fork 的报告形状一致，CI 只需要认一种结构。

## 决策六：旁路产物由父进程独占写盘

子进程带 `--no-side-outputs`，不写 HTML 报告、也不写**默认**的回放脚本；父进程合并后写**一份**脚本与**一份** HTML。

录制数据走 `--emit-script <临时路径>` 回传：父进程给每个子进程指定一个临时脚本（系统临时目录下，用完全退出时删除），收工后把这些脚本的 `scenarios[]` 拼成一份。也就是说 `--no-side-outputs` 关的是「默认产出」，**显式给出路径的 `--emit-script` 仍然生效**——这正是既有 ADR-0011 决策三「显式永远先生效」的自然延伸，不需要为子进程开特例。之所以不从 stdout 回传录制：报告的 stdout 契约只有一份 JSON，往里塞第二样东西就得改契约；而回放脚本本来就是现成的载体。

理由：回放脚本是一个源文件一份、内部带 `scenarios[]`；拆成「一个场景一份」会让「回放整份用例」这个动作失去对应文件，还要改 `--replay`、按来源分组与拍平一整套逻辑。

## 决策七：崩溃与超时都记失败，且不牵连别人

子进程非正常结束（崩溃、被强杀，或超过可配的场景级时长上限）记该场景为**失败**：`ScenarioDetail.reason` 写机器可读分类（`crash` / `timeout` / `infrastructure`）供 CI 判读，人读原因放 `summary`；随后**继续**执行后面的场景。只有当故障是基础设施级（`infrastructure`：模型端点不可达、bsk/浏览器不可用）时才取消剩余场景——与既有的「模型探活失败即取消剩余」同构。

父进程区分这两类的方式是**回头查一次**：子进程没交出报告时，父进程先探一次模型、再查一次 bsk 就绪；两者都健康，就只能是这个子进程自己崩了。刻意不做「开跑前统一探活」——子进程自己本来就会探活（口径与今天逐场景运行一致），父进程再加一次只会让每个场景都多付一次等待；只在「没交出报告」这个异常路口上付一次。

理由：崩溃和超时都不是用户意图，记成 `已取消` 会让它**静默逃过退出码**（已取消不计入退出码，等于把崩溃洗成通过）。造一条失败的假断言则更糟：既伪造数据，又会破坏「断言行数必须与断言结果数对齐」这条自检。

## 决策八：场景级时长上限默认关闭

新增可配的场景级上限，默认 `0`（不限）；一旦触发即按决策七处理。

理由：README 把「十几分钟的长流程」当常态，凭空定一个默认上限就是制造新的失败来源。CI 需要门禁时显式设置。既有的超时都是「贴着单条命令」的（bsk 命令默认 60s、download 等待上限可配、`wait-ms` 按等待时长放宽），场景级上限是**新增的一层**，不做默认值猜测。

## 决策九：子进程日志按行转发；串行不加前缀，并发加场景编号前缀

父进程 pipe 子进程的 stderr 并按行原样转发进自己的日志 sink：交互模式进日志视口，批处理进父进程的 stderr。

串行时逐字原样转发：父进程自己就会在边界上打「开始/结束」日志，顺序足以分辨；加 `[场景名]` 前缀会污染既有日志文案与 i18n 表。只在 `--debug` 时转发也不行——那等于把交互模式的核心体验砍掉。

并发时（决策三的并发路径）每行加 `[#k 场景名]` 前缀，`k` 是**用例原文里的次序**（与报告、`--only k`、看板编号同一个数）。前提没了做法就得跟着变：几条场景的日志必然交错，没有前缀就分不清哪一行属于谁，而「模型输出到哪了」只能靠日志判断。编号在前是因为它唯一且能拿去别处查，名字在后只作辨认、过长截断。

理由（补齐）：批处理与交互模式共用同一个前缀实现（`scenarioLogTag` + `RunChildOptions.logTag`），落在子进程协议层而不是各自的 sink 上——两处各写一遍，格式迟早会漂。用量行不加前缀：它被吞掉交给状态栏，不进日志流。父进程自己打的场景级日志（交互模式的「场景 #k 开始/结束」）带同一个编号，便于与前缀行对照。

## 实施时补齐的边界

- **占位符按场景各自展开**：子进程拿的是**未展开**的用例（文件路径或原文），自己展开一次——不这样写，录制回放脚本时就没法把具体值还原成 `${...}`。两条路径都一样：批处理把文件路径/原文交下去，交互模式把场景原文交下去。
  这会**部分取代 ADR-0002 决策六**（「追加场景与初始场景共用同一时刻」）：会话级的 `now`/`vars` 不再由 TUI 持有，`InteractiveOptions` 里的这两个字段已删除，每个场景各自展开。之所以敢这么做，是因为那条决策担心的「同一份脚本里一个占位符对应多个取值」在新录制里不成立——每个子进程都用**自己的**取值把字面量还原成 `${...}`，合并出来的脚本里占位符是唯一的；`deriveSubstitutions` 那条反查路径也本来就是「多个字面量 → 同一个占位符」的一对多映射。代价只剩一条：报告里各场景的时间戳不再相同，而时间戳的作用本来就是「不重名」。
- **子进程的命令行契约**（决策二的落地形态，已用单测钉死）：`--only <k> --json --no-tui --no-side-outputs --locale <lang> [--debug] [--session <id>] [--emit-script <临时路径>] [--usage-stream] -- <用例>`。`--locale` 必须显式传：父进程的语种可能来自 `--locale`，子进程从环境与配置里读不到它。
- **模型不可达的两副面孔**：第一个场景就不可达时，orchestrator 直接抛 `ModelUnreachableError`，CLI 打干净报错、**不给 stdout 塞报告**——与今天逐场景运行时的处置逐字一致；套件**中途**不可达时，已完成场景的报告照给（丢掉它们才是真的亏），坏的那个记 `infrastructure` 失败、剩余记「已取消」，并另补一条干净报错、退出码 1。
- **`--only` 要求用例真的按 `## 场景名` 分隔**：整份用例只有一个场景时，直接跑它就是它本身，`--only` 没有可指定的东西（报错而不是猜）。
- **子进程入口按模块位置解析，绝不用 `process.argv[1]`**（`resolveCliEntry()`）。这不是洁癖，是一次实测事故：`process.argv[1]` 只在「本进程就是 CLI」时才等于入口脚本，在被别的程序调用时（测试进程、将来的库用法）它是**调用方自己的文件**。第一版拿它当入口，于是测试进程里 fork 出来的子进程是「再跑一遍那份测试文件」，那份文件又会 fork……自我复制的死循环，浏览器窗口成串开出来（2026-09-28 现场）。改成 `new URL("./index.js", import.meta.url)`：谁调用都指向 CLI 自己，入口不存在就当场报错，不让 node 的「找不到模块」被当成子进程日志混过去。已用单测钉死这条不变量。

## 交互模式的两条跨进程通道（第二步）

场景搬进子进程之后，有**两样东西**原本是「同进程才拿得到」的，都必须显式开一条路。两条路都刻意走**已有的公开机制**，不发明内部暗规则：

1. **实时 token 用量 → `--usage-stream`**。状态栏那句「已经烧了多少」原本是 `onUsage` 回调推上来的。现在子进程把每次累计用量渲染成一行 `[pageqa:usage] {json}` 打到 stderr，父进程读到就吞掉（状态栏自己渲染）并回调 `onUsage`。做成明文可读的一行 + 公开开关：谁都能自己跑一次 `pageqa --only 2 --usage-stream …` 看到它，而不是只有内部人知道。批处理模式下这个开关同样生效（父进程原样转出来）。
2. **会话选定的模型 → 既有的 `PAGEQA_LLM_MODEL` / `PAGEQA_LLM_PROVIDER`**。`/model` 只改交互进程的内存，子进程从配置里读不到；而这两个环境变量本来就是 `loadConfig` 的合法输入，直接设给子进程即可，不需要新协议。凭据走 `~/.pageqa/auth.json` 或继承的环境变量，天然可用。

配套还加了 `EnvironmentUnavailableError`：父进程建 session 失败、或子进程没有报告且回查发现浏览器环境不可用，都归到这一类。交互模式据此停掉整条队列（与「模型不可达」同样的处置、不同的说法），批处理则把该场景记 `infrastructure` 失败、剩余记「已取消」。

## 未采纳的方案

- **并行跑多个场景**：跨进程没有 bsk 串行锁，「一次只有一条 bsk 命令在飞」失效，且窗口占用不受控。
- **让子进程上报 session id、父进程代为关闭**：崩溃/被强杀时 id 可能压根没上报，收尾逻辑在最需要时失效。
- **一个场景一份回放脚本**：`--replay` 的入口是整份用例，拆开后「回放整份用例」没有对应文件。
- **子进程输出单场景形态、父进程归一化**：同一个概念两种 JSON 形状，是后续 bug 的温床。
- **把崩溃写成一条失败的断言**：伪造数据，并破坏断言行数与断言结果数对齐的自检，还可能被录进回放脚本。
- **新增「已崩溃」终态**：看板带的 5 列与 `ScenarioState` 一一对应，加终态要动 UI 与所有报告消费方，收益不值。
- **父进程不走 CLI、直接 fork 内部入口**：违背决策二，让「单独重跑」与「内部隔离」分家。

## 影响

- `src/index.ts`：新增 `--only` / `--no-side-outputs` / `--usage-stream` / `--concurrency`；套件分支改走父进程编排，`--only` / 单场景两条分支保持原样并把用量回调接上。`--only` 与 `--suite` / `--tui` / `--replay` 互斥，且不自动进交互模式；`--concurrency > 1` 同理。
- `src/suite.ts`（新增）：父进程编排——fork、并发调度（`mapWithConcurrency`，默认 1）、stdout JSON 解析、stderr 按行转发、用量行拦截、上限看门狗、中止、session 预建与孤儿收尾、临时脚本合并、异常归因；外加交互模式用的 `runScenarioInChild`。
- `src/agent.ts`：`runSuite` **保持原样**（它就是 `--only` 与子进程内部跑的那条路径）；新增 `selectScenario` / `renderScenarios` 与归因用的 `probeModelReachable`。
