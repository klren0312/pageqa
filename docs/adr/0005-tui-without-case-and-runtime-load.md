# ADR-0005：无参进入交互模式，且用例文件可以在运行中加载

- 状态：采纳（2026-09）
- 修订：[ADR-0002](./0002-interactive-mode-and-stdout-contract.md) 决策七（「交互模式因此要求必须有源用例文件」）
- 背景：ADR-0002 决策三把「批处理 / 交互」的差别压缩到「有没有 TTY」，但入口仍要求先给一个用例文件——无参运行打印帮助并退出，`pageqa --tui "<内联文本>"` 直接报错（决策七）。于是「先开一个会话，再决定跑什么」做不到。本次让交互模式可以**没有源用例文件**地启动，并允许在运行中用 `/run` 把一个已有用例文件加载进来。

## 决策一：无参 + TTY 进入交互模式；没跑过任何场景不算失败

入口规则改成：**输入为空**时，TTY 下进交互模式，非 TTY 下维持「打印帮助 + 退出码 1」；`--tui` 无参在 TTY 下合法，非 TTY 仍报 `err.tuiNeedsTty`。自动识别只放宽了「没有输入」这一种情况——**给了输入仍按原规则**：给文件进交互，给内联文本走批处理。

`pageqa --tui "<内联文本>"` **仍然报错**（决策七的判决没有推翻，只是不再适用于「没有输入」）。理由：批处理与交互的差别本该是「人看不看这个终端」（决策三），若给内联文本加 `--tui` 才不写回、不加就走批处理，两种模式的差别就变成了「有没有 flag」，这正是决策三刻意避开的。代价是这条例外要解释一句，所以报错文案要写明出路（无参进交互，或去掉 `--tui` 走批处理）。

「进去看一眼、一个场景都没跑就退出」的收工口径：**退出码 0，stdout 不打印报告**，只在 stderr 说一句「本次没有运行任何场景」。TUI 只在 TTY 下发生，stdout 后面没有 CI 消费者；而一份 0 场景的空报告会打印出一个**没有内容的 PASS**——那是「假通过比报错危险得多」的另一副面孔。

## 决策二：`/run` 是显式命令，不做裸路径自动识别

加载用例文件用命令 `/run <路径或关键字>`，不采用「输入行看起来像用例文件路径就当作加载」。

理由是本仓库自己吃过的教训：`src/index.ts` 里 `--emit-script ./replay` 那次「静默把用例换成 `./replay` 去跑，看起来像正常启动、实际测的是完全无关的文本」。交互模式里同样的错误**更隐蔽**——全屏界面加滚动日志，你会看到「跑起来了」，很难发现跑的是别的东西。`/run` 另外还顺带承载了「关键字」这种写法，比自己发明一套裸路径识别干净。

## 决策三：候选由 pageqa 枚举，模型只挑文件名

`/run` 的解析分三层，**确定性优先**：

1. 精确路径（存在即加载）；`/run examples/` 这类目录则按 `examples/**/*.{md,txt}` 展开；
2. 关键字 → `**/*<关键字>*.{md,txt}`，排除 `node_modules/.git/dist`，命中上限 20；
3. 命中唯一 → 直接加载；命中多个 → 把**候选文件名列表**交给模型挑；模型挑不出、或模型不可用 → 弹 `SelectList` 浮层让用户自己选。

刻意**不**给正在跑测试的那个 agent 增加读文件工具。文件内容一旦绕过 pageqa 直接进模型上下文，步骤编号、`k ↔ 用例原文` 映射、写回、录制对应关系整条链全断（README「失败定位」整节的前提没了），而模型同时也获得了读取本机任意文件（`~/.pageqa/auth.json`、`.env`）的能力。把模型限制在「从文件名列表里挑一个」上，收益与风险的比例完全不同。

也刻意**不**全量枚举 cwd 下所有 `.md`——那会把 `README.md` 与 `docs/adr/*.md` 一起塞进候选，模型挑错的概率比挑对高，而它挑错时用户看不出来（照跑，跑的是另一个文件）。

## 决策四：场景来源成为一等属性，写回只发生在追加场景上

队列原来只有 `added: boolean`（是否用户追加），这个二分装不下 `/run` 加载进来的场景——它们不是用户提交的，也不该被写回（本来就在文件里）。因此引入**场景来源（Scenario Origin）**：某个用例文件，或用户在交互中的追加。`added: boolean` 换成一个带路径的来源。

由此得到一条单一事实，下游全部由它决定：**写回只发生在来源为「用户追加」的场景上，且写往当前落点。**

来源还必须**看得见**：一次会话可能混合多个用例文件与手敲的场景，而「跑 FAIL 的这个场景来自哪个文件」与「卡在第几步」是同一类定位信息（README「失败定位」整节的前提正是后者）——尤其当来源是运行中 `/run` 进来的时，用户手里根本没打开那个文件。因此报告的场景标题带来源标注（文本与 JSON 都带；批处理模式不带，输出与历史逐字一致）、`/status` 每条带来源、场景开跑那行对追加场景标「（追加）」。

落点（Write-back Target）= **最近一次显式加载的用例文件**（启动时指定或运行时 `/run`）。切换落点必须当场说出来（视口里一行「写回落点已切换为 `<path>`」），状态栏常驻显示当前落点。不采用「落点首次填充后不再变」——那会造成更难的意外：「我刚打开 B 文件，敲下的用例却写进了 A」。

不采用「每条追加场景各自选落点」：它把「每敲一条用例都多一步」变成常态摩擦，换来的只是偶发场景的安全。

## 决策五：加载是追加到队尾，不是替换

`/run` 只是**一次批量提交**，正在跑的场景不受影响，新场景排在待办后面。队列对用户的承诺是「提交了就一定会跑」（ADR-0002 决策五），而加载本身是个只读动作——让它带上破坏性（清空待办、中止当前）得由用户明说。想换任务的人已经有 `/cancel` 与 Ctrl+C（取消全部待办）。

## 决策六：没有落点就不写回，但必须说出来

ADR-0002 决策七的三条硬约束——写回的是用户输入的原文（含占位符）、用 `appendFile` 不重写整个文件、写回格式与 `splitScenarios` 的解析规则严格对齐——一条都不动。被放开的是它的推论「必须有源文件」：没有落点时，追加场景只存在于本次会话，**不写任何文件**。

（「凭空造一个文件当落点」是决策七明确拒绝过的：不在用户工作目录里造文件，也不静默降级。）

代价是引入了一个**正常但会丢数据**的状态——它与「写回失败」（异常，有 `tui.writeBackFail` 兜着）不是一回事。因此：

- 提交时若无落点，视口里明说这一条不会写回；
- 退出时若存在没写回过的追加场景，在汇总报告前打一行「本次有 N 个追加场景没有落点、未写入任何文件」（有落点时不打）；
- `log.wroteBackScenarios`（「已写回 N 个场景到 `<file>`」）在无落点时不能播报，换成上面这句。

理由：写回的时机是「提交即落盘」，这个设计本来就是用**「敲下去就等于留下了」**换取安全感的。无落点把这个前提抽掉了，那就必须有人把话说出来，而不是静默丢数据。

## 决策七：回放脚本按来源拆，不动脚本格式

`ReplayScript.source: { path, hash }` 是**脚本级单值**，而一次会话现在可以加载多个用例文件。不升级脚本格式（`sources[]`），而是**按来源拆脚本**：每组来源各自写一个贴着源用例的 `<名>.replay.json`。

分组规则：来自文件的场景归它的来源文件；用户追加的场景归**提交时的落点**——因此**只有一个文件时，产出与今天完全一致**；从没加载过任何文件、纯内存追加的场景，合并写 cwd 的 `pageqa.replay.json`（与内联文本的默认位置一致，沿用既有先例）。

不升级格式的理由不是实现难度，而是**脚本是唯一会被用户长期保存、丢进 git、并在 CI 里零模型重跑的对外契约**（`--replay` 的输入格式）。升级会让一份脚本有两种可能的结构，`loadReplayScript`、`sourceDriftNotice`、`normalizePlaceholderLiterals` 全要双分支，换来的只是「一份脚本装多个来源」——而真实使用中几乎不会在同一次会话里把两个用例文件都跑通再一起固化。

两处配套判决：

- **显式给了 `--emit-script <path>` 而本次运行有多个来源 → 报错**，直说「本次运行有 N 个来源，一个脚本装不下；去掉路径让它们各自贴着源用例写出，或分两次运行」。不静默只收其中一个。这条报错本身也是文档：回放脚本与用例文件是一对一的（ADR-0001）。
- **一个场景都没跑时（0 场景）不落盘**，只打一行「本次没有跑过任何场景，未生成回放脚本」。「跑过但一步都没成功」维持现状照写——那是**证据**（READM 明说 PASS/FAIL 都生成，便于排查模型这次做了什么），而 0 场景连证据都没有，落盘只会多一个需要判断「这个空脚本是什么」的文件。

## 决策八：加载场景的占位符共用会话时刻（决策六 + 决策七的推论）

运行时 `/run` 加载的场景，其 `${timestamp}` 必须用**会话启动那一刻**展开，不能各用各的加载时刻。

这不是取舍，是必然推论：按决策七的分组，同一个落点文件派生的场景会进同一份脚本，而这份脚本里同时存在追加场景（按 ADR-0002 决策六用会话时刻）与加载场景；`deriveSubstitutions` 靠「一个占位符 ↔ 一个录制字面量」反查还原，一份脚本里 `${timestamp}` 若对应两个时刻，还原就含糊了——而回放端是全脚本只展开一次。

之所以写进 ADR：不写下来，下一个人很可能把它「顺手修好」成加载时刻。

## 考虑过的其他方案

- **给 agent 加读文件工具，让它自行查找并读取用例文件**：见决策三。
- **裸路径自动识别**：见决策二。
- **全量枚举 cwd 下的 `.md`**：见决策三。
- **无落点时凭空造一个用例文件当落点**：决策七明确拒绝过。
- **首次追加时弹选择器问落点 / 启动即要求选一个文件**：为「偶尔才用一次的路径」加常态摩擦。
- **落点首次填充后不再变**：见决策四。
- **每条追加场景各自带落点**：见决策四。
- **`/run` 替换队列（或中止当前场景）**：见决策五。
- **`pageqa --tui "<内联文本>"` 顺势解禁**：见决策一。
- **退出时阻塞确认「有场景没写回」**：退出要干脆，Ctrl+C 的语义是「我不想再等了」（决策五）。
- **脚本格式升 v2、`sources[]` 多来源**：见决策七。

## 影响

- 入口：`src/index.ts` 的 `detectInteractive` / `main`（无参分支）、退出时的脚本生成改为按来源分组、显式路径冲突检查；批处理路径行为不变。
- 交互：`src/tui/app.ts` 新增 `/run`（含候选解析与选择器兜底）、落点状态与状态栏、退出提示；`src/tui/queue.ts` 的 `added` 换成场景来源；`src/tui/writeback.ts` 增加「读入一个用例文件的场景」；新增 `src/tui/case-source.ts`（`/run` 的候选解析与「让模型只挑文件名」的提示/解析，纯函数便于单测）。
- 脚本：`ScenarioRecording` 带上来源，新增按来源分组组装脚本的函数（`buildReplayScript` 的签名与脚本格式不变）。
- 报告：`ScenarioDetail` 增加可选来源字段，文本报告的场景标题带来源标注。
- 文档：`CONTEXT.md` 新增「场景来源」与「落点」两条、修订「场景」与「交互模式」；README 两个语种同步。
