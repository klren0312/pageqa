# bsk 操作层全面异步化，并让 AbortSignal 贯穿到子进程

状态：accepted

`src/bsk/tools.ts` 的每条浏览器命令都经 `bsk()` 用 `execFileSync` 执行——**同步阻塞整个事件循环**，单条超时上限 60s。批处理模式下这无伤大雅（跑完就退出，没人需要在这期间按键），但交互模式下它同时废掉两件事：

1. **「执行期间还能输入」变成半真承诺**。命令执行期间界面不渲染、不收键，spinner 不转，打的字要等这条命令返回才出现。多数命令亚秒级、且大部分墙钟时间花在异步的 LLM 流式输出上（那期间界面是活的），所以多数时候感觉不到；但 `navigate` 打开重页面、以及 bsk daemon 卡住吃满 60s 超时这两档会明显冻住。
2. **Esc 无法真正中断浏览器动作**。`agent.abort()` 只 abort 它自己的 `AbortController`，不会替工具杀进程；而工具层目前连 `signal` 参数都没接。结果是「中止」只能等当前那条 bsk 命令自己跑完。

## 决策：操作层全异步，`signal` 一路传到 `child.kill()`

`bsk()` 改用异步 `execFile`（promisify），`createBskOps` 的所有方法 async 化；每个 `AgentTool.execute(_id, params, signal)` 接住第三个参数（`AgentTool` 的定义里本来就有 `signal?: AbortSignal`，由 `agent.abort()` 驱动，见 `agent-loop.ts:773-800`），在 `signal` 上挂 abort 监听并 kill 子进程。60s 超时同时改为**可被 signal 提前打断**，避免 daemon 卡死时界面被冻满一分钟。

这不是新踩的坑，而是**同一个坑的第二次出现**：`bskStatusJsonAsync` 的注释里已经写过——「同步子进程调用会阻塞整个进程，导致启动等待期（最长 30s）无法响应 Ctrl+C」。当时只为 daemon 轮询开了异步的口子，操作层没动；这次把它收口。

## 后果

- **串行性要显式保证**。现在「一次只有一条 bsk 命令在飞」是同步调用免费提供的；异步化之后，回放引擎与工具层都必须自己保证不并发下发命令（否则 `@eN` 引用与页面状态会互相踩）。
- **回放引擎跟着改**。`src/replay.ts` 直接复用操作层（这正是 ADR-0001「录制时怎么操作，回放时就怎么操作」的设计），ops 签名 async 化后它要一起改。
- **工具必须真的监听 `signal`**。只把 `signal` 接进签名而不 kill 子进程，等于什么都没做——这次改动的一半价值在监听那一行上。

## 考虑过的其他方案

- **保持同步，接受界面在 bsk 调用期间冻结**：改动面最小，但要接受「阶段性冻屏 + Esc 只能尽快停」，与本次「执行期间能交互」的目标直接冲突。
- **把同步操作放进 Worker 线程**：能保持同步写法又让出主线程，但要把 ops 与其状态（session、快照缓存、录制器）一起搬进 Worker，消息往返会污染「一条命令一个返回值」的简单模型，收益不抵复杂度。
- **只在 UI 层容忍（用 spinner 假装界面活着）**：自欺，排除。
