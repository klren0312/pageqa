# ADR-0007：滚轮被终端翻译成 ↑/↓ 时，把 ↑/↓ 分派给日志视口

- 状态：采纳（2026-09）
- 背景：用户报告「日志区域无法用鼠标滚动，滚轮反而把输入框的历史顶了出来」。线索很明确：**滚轮变成了 `↑`/`↓`**。应用侧并没有漏掉鼠标，`TuiAltScreen({ mouse: true })` 在进入 alt 屏后立刻发出了完整的鼠标上报序列（`\x1b[?1000h 1002h 1003h 1004h 1006h`，已用无头探针逐条核对）。因此这是终端侧行为：一部分终端在应用拿不到、或忽略鼠标事件时，会把 alt 缓冲里的滚轮**翻译成方向键**（VS Code 的 xterm.js 就是这样，目的是让 `less`/`man` 这类程序仍能翻页）。方向键落进输入框后，编辑器在输入框为空时会把它当作历史浏览——于是「滚轮一滚，上一次提交的文本就被顶进输入框」，而日志一行都没动。

## 决策一：承认滚轮与真方向键不可区分，按上下文分派

不去「修终端」（做不到），而是承认两者**字节相同**，按上下文分派：**输入框为空时 `↑`/`↓` 归日志视口**，否则归编辑器。这是唯一能让「滚轮能滚日志」与「多行用例照常编辑」同时成立的切分点——空输入框上 `↑`/`↓` 本来也没有编辑语义。

## 决策二：历史输入挪到 `Ctrl+P` / `Ctrl+N`

`↑` 在空输入框上只承担「历史浏览」这一件事；把这件事挪走，`↑`/`↓` 才能给滚轮让路。选 `Ctrl+P`/`Ctrl+N` 是因为它们是 readline 的老习惯，且在 pi-tui 的默认键位里是空的（不会盖掉任何既有能力）。两条路都走得通：`Ctrl+P` 调出历史文本后输入框立刻非空，`↑`/`↓` 马上回到编辑器手里继续翻历史。

## 决策三：先把方向键让给浮层与联想列表

浮层（`/model`、`/run`、登录选择）与 `/` 命令联想都靠 `↑`/`↓` 选条目。它们是「更近的消费者」，因此分派的前置条件是 `overlayOpen` / `autocompleteShowing` 都为假——否则会出现「列表在等方向键，却被日志抢走」这种选不中条目的坏体验。

## 决策四：步长与滚轮一致，并保留一条「任何时候都生效」的逐行滚动

既然滚轮与 `↑`/`↓` 不可区分，两者步长就该一致（3 行）。同时保留 `Ctrl+↑`/`Ctrl+↓` 作为逐行滚动：它在输入框非空、多行编辑时同样生效，给键盘用户的精细控制留一条不被上下文的干扰的路。

## 决策五：只吃「按一下」，不吃 Kitty 协议的释放事件

支持 Kitty 键盘协议的终端会额外上报 key release。若不看 `isKeyRelease`，一次滚轮会在那类终端上滚两倍。

## 未采纳的方案

- **`↑`/`↓` 一律改成滚动日志**：多行用例编辑时 `↑`/`↓` 是光标移动（ADR-0002 决策三要求输入框支持 `Shift+Enter` 多行），一律抢走会毁掉编辑。
- **检测「到底是滚轮还是方向键」**：字节层面做不到。
- **要求用户改终端设置或换终端**：等于不修。
- **`↑`/`↓` 先滚日志、滚到顶再翻历史**：行为随视口位置变化，既无法预期也无法解释。
- **加一个 CLI 开关**：把「用户用哪个终端」的差异做成配置项，负担落在最不该承担的人身上。

## 影响

- 新增 `src/tui/keys.ts`：键位覆盖（`tui.altScreen.lineUp/lineDown`、`previousPrompt`/`nextPrompt` 让位、历史键位）+ 滚轮步长 + `arrowKeysBelongToLog()`（纯函数，可单测）。
- `src/tui/app.ts`：全局输入监听接管 `↑`/`↓`（输入框为空时交给视口）；文件头键位说明同步。
- 文档：`/help` 的「日志视口」段、底部提示行、README 两个语种的键位表与说明。
- 测试：`tests/tui.test.mjs` 覆盖键位（历史挪到 `Ctrl+P`/`Ctrl+N`、不碰编辑器编辑键、无冲突）与 `arrowKeysBelongToLog()` 的分派规则。
