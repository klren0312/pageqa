问题：重页面上 bsk 快照有 684 个 @eN 可交互元素行（35.9k 字符），而 src/snapshot.ts 规定这些行「永不截断、永不丢弃」—— 于是 20k 字符预算在引用数超过约 210 时必然击穿（实测超 3.3×），单次快照还比 40k 的上下文中限更大。
如果按「同名折叠 → 剥标注 → 降级为计数」逐级砍这些行，语义定位（role + name + 祖先路径 + 同名序号）还能把每个定位符解析回它原本那个 @eN 吗？
判据：把页面上每一个可交互元素都当成「录制时点过的元素」建定位符，再拿瘦身后的文本重解析。 命中 = 解析回原来那个；指错 = 落到别的元素（假通过，最危险）；未命中 = 回放按「跳过」处理。 三页数据都是真实抓的快照，不是构造样本。
跑出来的答案：能压，但不是靠丢引用，而是靠把同名叶子折叠成一行 —— 跨区块折叠把重页从 65,437 → 38,462 字符（交给模型的上下文省 41%）， 684 个引用全部仍可寻址，且指错从现状的 16 条降到 0；中等页面（Form 页 450 引用）直接进 20k 预算（19,986）。 两个反直觉的结论：①「折叠时花字符补回祖先路径」是净亏（字符只省 5%，指错反涨到 105）；②「降级成纯计数以省字符」等于毁掉定位（514 条指错）。 另外：抓取耗时由原始大小决定（瘦身在抓取之后），所以这档瘦身省的是上下文与 token，不是那 ~2.8s 的往返。
